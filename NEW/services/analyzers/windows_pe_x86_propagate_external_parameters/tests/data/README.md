# Analyzer Name
WindowsPE x86 Propagate External Parameters

## Purpose
Exercise propagation of external function parameter names/types from x86 PUSH instructions and address operands.

## Original Ghidra Implementation
`Ghidra/Features/MicrosoftCodeAnalyzer/src/main/java/ghidra/app/plugin/prototype/MicrosoftCodeAnalyzerPlugin/PropagateExternalParametersAnalyzer.java`.

## Test Scenario
Four real x86 pushes precede a call through a naked import thunk to `MessageBoxA`; the script snapshots the imported signature, propagated EOL comments, data rows, and candidate references before and after target analysis, with explicit deltas.

## Why This C++ Code Was Chosen
The x86 calling convention and literal PUSH mnemonics are the analyzer's actual eligibility contract, so a 64-bit substitute would be invalid.

## Required Compiler Options
MSVC x86 environment selected by `VsDevCmd.bat -arch=x86`, as invoked by `build.bat`.

## Required Auxiliary Files
The Windows SDK import library, matching PDB, PE loader, and `TEST/run_ghidra_python.bat` are required.

## Ghidra Analysis Options
Enable the named byte analyzer and its explicit `PDB Universal` dependency as configured by `run_ghidra.py`.

## Expected Results
The report requires four propagated PUSH comments, lists the source-declared `parameter_*`
data symbols, and records the imported prototype and candidate CALL/PUSH instructions as
supporting setup evidence rather than analyzer changes.

## Generated Markdown
`test_windows_pe_x86_propagate_external_parameters.md` is generated by `run_ghidra.py`.

## Notes / Limitations
The implementation is x86-specific and depends on imported prototype/PDB state; an x64 build would not exercise the requested paths. The existing sections below retain reproduction details.

This directory contains a dedicated 32-bit MSVC PE for the analyzer named
`WindowsPE x86 Propagate External Parameters`. The source makes a real `__stdcall`
call through a naked import thunk to `MessageBoxA` after four ordinary x86 `PUSH` instructions. The
generated report records the analyzer's four EOL parameter comments, the actual
source-declared `parameter_*` data symbols, and any plate comments it creates for address operands.

## Why x86 is mandatory

The exact implementation is
`Ghidra/Features/MicrosoftCodeAnalyzer/src/main/java/ghidra/app/plugin/prototype/MicrosoftCodeAnalyzerPlugin/PropagateExternalParametersAnalyzer.java`.
Its `added()` method (lines 240-307) iterates external function symbols and only
processes ordinary `CALL` instructions (lines 52-75). `hasEnoughPushes()` (lines
157-180) and `propogateParams()` (lines 182-226) explicitly compare the mnemonic
to `PUSH`, and the later address-reference test uses x86 operand flags (lines
274-305). A 64-bit fixture would therefore not exercise this contract. The x86
build flags and source are intentional, not an optional alternate build.

The PDB is an explicit analysis dependency for source-level function context. Before
any disassembly or manual signature setup, `run_ghidra.py` verifies the supplied PDB's
file name, GUID, and age against the executable's CodeView metadata, then requires
`PDB Universal` to report the PDB as loaded. The PE import loader exposes `MessageBoxA`
as an external function but does not transfer the source declaration's type to that
external address in standalone PyGhidra. The harness therefore applies the
four-parameter import prototype as a documented, transactional analyzer precondition
before invoking the real target analyzer; it does not synthesize target comments,
labels, data, or report rows.

Run `build.bat`, then execute
`TEST\\run_ghidra_python.bat \features\\analyzer\\test_data\\windows_pe_x86_propagate_external_parameters\\run_ghidra.py`
from the repository root.
