# Analyzer Name
Windows Resource Reference

## Purpose
Exercise resolution of constant resource IDs and creation of DATA references to loader-created resource data.

## Original Ghidra Implementation
`Ghidra/Features/MicrosoftCodeAnalyzer/src/main/java/ghidra/app/plugin/prototype/MicrosoftCodeAnalyzerPlugin/WindowsResourceReferenceAnalyzer.java`, which invokes `Ghidra/Features/Decompiler/ghidra_scripts/WindowsResourceReference.java`.

## Test Scenario
Real STRINGTABLE, DIALOGEX, and MENU resources are referenced by two constant `LoadStringW` calls; the script snapshots loader resources and DATA references before and after the target, then reports explicit deltas.

## Why This C++ Code Was Chosen
Actual `.rc` compilation and loader-created resource symbols test ID resolution rather than merely detecting an `.rsrc` section.

## Required Compiler Options
MSVC x64, Windows SDK `rc.exe`, and linker options from `build.bat`.

## Required Auxiliary Files
`test_windows_resource_reference.rc`, `resource.h`, Windows SDK tools, the PE loader, and `TEST/run_ghidra_python.bat` are required.

## Ghidra Analysis Options
Enable only `WindowsResourceReference` after explicit disassembly; the script initializes the Ghidra script bundle host required by the wrapper.

## Expected Results
Loader resource symbols and DATA references for the constant IDs should be present and are extracted from the saved program. The report separately records the numeric resource ID/table and the locale suffix, validates the matching PDB, and distinguishes loader setup symbols from target-created DATA-reference deltas.

## Generated Markdown
`test_windows_resource_reference.md` is generated by `run_ghidra.py`.

## Notes / Limitations
Resource layout and script-bundle availability are environment dependent; the fixture does not hand-author loader resource rows. The report's verification table is derived from the real `.rc` and `resource.h` inputs.

This directory contains a CRT-free MSVC x64 PE with resources compiled by the real
Windows `rc.exe`. The code calls imported `LoadStringW` twice with constant string
IDs. The `.rc` file also contains a dialog and menu so the report records multiple
resource types, IDs, and loader addresses instead of treating `.rsrc` as arbitrary
bytes.

## Original implementation

The analyzer wrapper is
`Ghidra/Features/MicrosoftCodeAnalyzer/src/main/java/ghidra/app/plugin/prototype/MicrosoftCodeAnalyzerPlugin/WindowsResourceReferenceAnalyzer.java`.
Its `canAnalyze()` method (lines 60-67) requires the PE format and `added()` (lines
69-73) invokes `WindowsResourceReference.java`. The script's exact resource routine
list and argument indexes are in
`Ghidra/Features/Decompiler/ghidra_scripts/WindowsResourceReference.java` lines
135-225. `analyzeFunction()` lines 364-423 follows constant P-code arguments, while
`addResourceReferences()` and `addResourceTableReferences()` lines 460-537 create
analysis DATA mnemonic references. `findResource()` lines 547-610 maps IDs into the
resource data symbols created by the PE loader.

The fixture uses actual `.rc` syntax and `rc.exe`; no resource table or output row is
handwritten. Run `build.bat`, then execute
`TEST\\run_ghidra_python.bat \features\\analyzer\\test_data\\windows_resource_reference\\run_ghidra.py`
from the repository root.
